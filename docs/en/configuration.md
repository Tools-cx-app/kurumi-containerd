## File location and container selection

CLI and TUI read `$HOME/.kurumi-containerd/config.json`. `HOME` must be absolute
and belongs to the running process; `sudo -H` normally selects root's HOME.
Most commands require an existing registry. Both `install` and `import` can
create one. `install` saves a missing entry before extraction. `import` adds its
new entry after installing the rootfs. Invalid JSON, unknown fields and invalid
values produce errors. See [installation](usage.md#install-a-local-rootfs) and
[portable packages](usage.md#portable-packages).

The top level is a nonempty list of complete configuration objects:

```json
[
  {
    "runtime": {},
    "container": {
      "name": "debian",
      "rootfs": "/srv/kurumi/debian/rootfs"
    }
  }
]
```

Each object requires `runtime` and `container`. Names are unique and
case-sensitive. A sole entry is selected automatically; with multiple entries,
put `--name NAME` before the command. For `backup` and `export`, give the source
name as the positional `CONTAINER_ID` and omit `--name`. For `import`, `--name`
sets the destination name, which defaults to the name recorded in the package.
The TUI lists all entries. `check` and `import PACKAGE --inspect` work without
HOME or a registry.

There are no outer `name`/`file` pointers, standalone TOML loading,
`-c/--config`, or `KURUMI_CONTAINERD_CONFIG`. See the
[migration guide](migration-config-pointer.md) for older installations.

## Paths and persistent identity

Relative host paths resolve from the directory containing `config.json`:
`rootfs`, `rootfs_image`, bind-mount `source`, `environment_file`, and `binfmt.interpreter`.
Paths do not expand `~` or environment variables. `init` and mount `target`
refer to paths inside the container, even when they begin with `/`.

Normal runtime commands persist a missing UUID in the selected entry. The
atomic rewrite preserves other entries, ownership, permissions and a symlink
to the configuration file. Existing UUIDs remain unchanged. Installation,
backup, export and read-only TUI refresh do not persist missing UUIDs. Import
assigns a fresh UUID and a local rootfs path. Back up `config.json` separately
to preserve the full registry and its original UUIDs.

## Runtime settings

| Field in `runtime` | Default | Meaning and validation |
| --- | --- | --- |
| `stop_timeout_seconds` | `15` | Graceful-shutdown timeout in seconds; must be greater than zero |

Runtime files live in `/run/kurumi-containerd` on Linux and
`$TMP/kurumi-containerd` on Android. The directory must be root-owned, must not
be group/world writable, and must not be a symlink. There is no configurable
work-directory field.

## Container settings

| Field in `container` | Default | Meaning and validation |
| --- | --- | --- |
| `name` | Required | ASCII letters, digits, `.`, `_`, `-`; nonempty, excluding `.` and `..` |
| `uuid` | Absent | Persistent UUID; generated by normal runtime loading when missing |
| `rootfs` | Absent | Host directory; configure exactly one of this and `rootfs_image` |
| `rootfs_image` | Absent | Host filesystem image or block-device path |
| `hostname` | Container name | Empty or omitted values use `name` |
| `init` | `/sbin/init` | Absolute path inside rootfs |
| `binfmt` | Absent / `null` | Optional foreign ELF architecture and static host interpreter, described below |
| `isolation` | `isolated` | `isolated` or trusted `shared-pid-ipc`; shared mode requires cgroup v2 |
| `foreground` | `false` | Connect start/restart to a foreground console |
| `volatile` | `false` | Put writable OverlayFS layers on tmpfs; changes are discarded |
| `network` | `host` | `host`, `none`, `nat`, `gateway`, or `dhcp` |
| `network_options` | Defaults below | Network addresses, bridge, DNS and port forwarding |
| `resources` | No configured limits | cgroup limits described below |
| `security` | Defaults below | Kernel views and nested user namespaces |
| `environment` | `{}` | String-valued environment assignments |
| `environment_file` | Absent | Host environment-file path |
| `mounts` | `[]` | Bind mounts described below |
| `android` | All flags `false` | Android host integration described below |

Normal loading requires an existing rootfs and, for directory roots, the
configured init path. `install` allows a missing target: it installs a local
archive into `rootfs`, or creates a sparse ext4 `rootfs_image` with `--size SIZE`.
Existing targets require `--force`. See [installation](usage.md#install-a-local-rootfs).

The following examples are object fragments to merge into the selected entry,
not complete configuration files. [config.example.json](../../config.example.json)
provides a larger example; adapt its paths and remove mounts you do not need.

## Cross-architecture execution with binfmt_misc

Set `container.binfmt` when the rootfs contains programs for another architecture.
For example, on an ARM64 Linux/Android host with a static x86-64 QEMU user emulator:

```json
{
  "container": {
    "binfmt": {
      "arch": "x86_64",
      "interpreter": "/usr/bin/qemu-x86_64-static"
    }
  }
}
```

The interpreter is a **host** path, resolved relative to `config.json` when relative.
Supply a regular executable ELF file, statically linked for the host architecture.
It is not downloaded or copied into rootfs. The kernel must support
`CONFIG_BINFMT_MISC` and the `F` flag (Linux 4.8 or newer); an unavailable or disabled
registry causes startup to fail with an error. Omit `binfmt` or set it to `null`
for native containers. Specifying the runtime's native architecture is rejected.

Supported architectures match [ruri](https://github.com/RuriOSS/ruri): `aarch64`,
`alpha`, `arm`, `armeb`, `cris`, `hexagon`, `hppa`, `i386`, `loongarch64`, `m68k`,
`microblaze`, `mips`, `mips64`, `mips64el`, `mipsel`, `mipsn32`, `mipsn32el`,
`ppc`, `ppc64`, `ppc64le`, `riscv32`, `riscv64`, `s390x`, `sh4`, `sh4eb`, `sparc`,
`sparc32plus`, `sparc64`, `x86_64`, `xtensa`, and `xtensaeb`.
Aliases include `arm64`/`armv8`, `armhf`/`arm32`/`armel`/`armv7`, `x86`,
`amd64`, and `loong64`/`loongarch`.

The monitor registers ELF magic/mask rules with `OCF`: the interpreter stays open
across root changes, the kernel supplies the executable descriptor and credentials,
and QEMU receives its normal argument layout. This covers init and subsequent
`run`/`enter` commands, including across container reboots. Each monitor owns a
unique `kurumi-*` entry and unregisters it after shutdown or startup failure.
Existing entries are preserved, and the registry is never globally cleared or enabled.

Rules are shared within the host user namespace, including on kernels without
user-namespace support for binfmt_misc. Other processes can use the registered
interpreter; the newest matching rule takes precedence. Concurrent containers
for the same guest architecture should use a compatible interpreter. If the
monitor is killed with `SIGKILL`, its destructor cannot run: a rule may remain
until explicitly unregistered through the host's binfmt_misc filesystem or reboot.

The privileged regression script builds a minimal foreign static init and checks
boot, `run`, PTY `enter`, reboot, concurrent registrations, and cleanup after stop
or failed boot. On an ARM64 host with the corresponding QEMU and cross compiler:

```sh
cargo build --release -p kurumi-containerd
sudo python3 tests/binfmt.py target/release/kurumi-containerd \
  /usr/bin/qemu-x86_64-static x86_64 x86_64-linux-gnu-gcc
```

It uses temporary rootfs directories and a private mount namespace. Extra compiler
options can be supplied as repeatable `--cflag=OPTION` arguments.

## PID and IPC isolation

`container.isolation` accepts `isolated` (default). Builds with the optional
`servicectl` Cargo feature also accept `shared-pid-ipc`; CI enables this feature
only for release artifacts. Local builds require `--features servicectl`, independently of the build profile.
Unknown values are rejected. There is no automatic fallback when namespace
creation fails. Shared mode inherits the PID/IPC spaces of Kurumi's execution
environment, including an outer container if one exists. Mount and UTS namespaces,
private `/run`, `/dev` and `/dev/shm`, procfs and existing security filters remain
required. `network: "host"` uses the existing `/proc/self/ns/net` handle without creating a new network namespace.

```json
{
  "container": {
    "name": "debian-services",
    "rootfs": "/srv/kurumi/debian/rootfs",
    "init": "/usr/local/sbin/kurumi-services",
    "isolation": "shared-pid-ipc",
    "network": "host"
  }
}
```

Shared mode always requires a writable, exclusively owned cgroup v2 subtree and
the ability to create a cgroup namespace rooted at its init leaf. Kurumi creates
an empty namespace root, mounts cgroup v2 there, and runs the supervisor in its
`bootstrap` child. cgroup v1 is unsupported in this mode. Old kernels without
`cgroup.kill` use repeated membership enumeration and trusted process handles;
that file is not a prerequisite. Controllers are required only for requested
resource limits. A missing PID/IPC namespace procfs interface is allowed.

This is a trusted-workload mode, not a security sandbox. Host processes are
visible through procfs, and SysV IPC and POSIX message queues are shared. Private
`/dev/shm` does not provide IPC namespace isolation. Services must clean only their
own IPC objects; Kurumi never globally deletes shared IPC resources.

Normal systemd system instances and other PID-1-dependent init programs are
unsupported. A custom entry must remain a foreground supervisor, handle SIGTERM
and exit after graceful cleanup. It must never call host shutdown/reboot tools,
`kill(-1)`, global `killall`, or global IPC cleanup. Arbitrary scripts cannot be
fully inspected for these operations. Init and exec/login inherit a reboot syscall
denial policy. Restart with Kurumi `restart`, not namespace reboot or SIGHUP.

Use the deployable [Dinit + s6/servicectl example](servicectl.md). Its dependencies
live in the rootfs; Kurumi has no Go runtime/build dependency on servicectl.
Only supported unit directives are translated: `PrivateIPC=` and full systemd
distribution boot semantics are not promised.

The actual isolation mode is persisted with each running generation. Changing
JSON does not change `run`, `enter`, `info`, `stop` or `scan` for that generation;
new settings apply at the next start. `check` remains independent of HOME/config
and reports mode prerequisites separately; `start` checks the selected workload.


## Networking

| Mode | Behavior |
| --- | --- |
| `host` | Share host networking |
| `none` | Use an isolated network namespace |
| `nat` | Configure a private network with host NAT and optional port forwarding |
| `gateway` | Attach a veth to the existing `gateway_bridge` with static addressing |
| `dhcp` | Attach to the existing `gateway_bridge` and run a DHCP client inside rootfs |

```json
{
  "container": {
    "network": "nat",
    "network_options": {
      "address": "172.28.0.2",
      "gateway": "172.28.0.1",
      "prefix": 16,
      "bridge": "kurumi-br0",
      "gateway_bridge": "",
      "dns": ["1.1.1.1", "8.8.8.8"],
      "ports": [{"host": 8080, "container": 80, "protocol": "tcp"}]
    }
  }
}
```

The addresses, prefix, bridge names and DNS above are the defaults; `ports`
defaults to an empty list. `address` and `gateway` are IPv4 addresses; DNS entries
must be IP addresses. Prefix must be at most 32. Each forwarding rule requires
nonzero `host` and `container` ports in the 16-bit range; `protocol` is `tcp`
(default) or `udp`. Within one protocol, duplicate host ports or duplicate
container ports are rejected. Port ranges are unsupported.

NAT and bridge setup use `ip` on the host and in the rootfs. NAT also uses host `iptables`. `gateway` and
`dhcp` require a valid `gateway_bridge` naming an existing bridge; the runtime
does not create or manage that bridge. DHCP uses the first client found inside
rootfs: `udhcpc`, `dhclient`, then `dhcpcd`.

```json
{
  "container": {
    "network": "dhcp",
    "network_options": {"gateway_bridge": "br0"}
  }
}
```

Changes to networking or resource settings apply on the next start. `enter`
and `run` join the running container's actual namespaces and cgroups.

## Resource limits and security

```json
{
  "container": {
    "resources": {
      "memory_bytes": 536870912,
      "cpu_quota": 100000,
      "cpu_period": 100000,
      "pids": 512
    },
    "security": {
      "read_only_sys": true,
      "allow_user_namespaces": false
    }
  }
}
```

In isolated mode resource limits use cgroup v2 when available and otherwise fall back to cgroup v1. Shared mode always requires cgroup v2. Memory must be at least 4 MiB. CPU quota and period must be configured together; quota must be at least 1000, and period must be greater than zero. Both use microseconds. The PID limit must be between 1 and 4194304. Unavailable requested controllers are reported as errors.

`read_only_sys` defaults to `true`; `allow_user_namespaces` defaults to `false`.
Enable the latter only for trusted workloads needing unprivileged user
namespaces, such as Docker userns-remap, Podman, Flatpak or Bubblewrap. The
normal hardened `/proc` and `/sys` remain, alongside fresh mounts at
`/run/kurumi-containerd/proc` (writable) and `/run/kurumi-containerd/sys`
(read-only). The extra proc view can expose host kernel sysctls and weakens
isolation. Container root retains capabilities; this is not a hostile-workload
security boundary.

## Environment and bind mounts

```json
{
  "container": {
    "environment_file": "./container.env",
    "environment": {"LANG": "C.UTF-8"},
    "mounts": [
      {"source": "./shared", "target": "/mnt/shared", "read_only": false}
    ]
  }
}
```

Environment files accept `KEY=VALUE`, optional `export`, comments, quoted and
empty values, and values containing `=`. Inline assignments override file
assignments. Keys must be valid environment-variable names and values cannot
contain NUL bytes. The environment file must exist.

Each mount requires an existing host `source` and an absolute, non-root container
`target` without parent traversal. `read_only` defaults to `false`. Bind mounts
expose host data to the container; rootfs backup does not include their sources.

## Android integration

All fields in `container.android` are booleans defaulting to `false`:

| Field | Host resource or effect |
| --- | --- |
| `storage` | Bind `/storage/emulated/0` into the container |
| `gpu` | Expose matching DRI render, KGSL, Mali and video devices |
| `binder` | Expose `/dev/binder`, `/dev/hwbinder` and `/dev/vndbinder` |
| `termux_x11` | Bind the Termux X11 `X5` socket to `/tmp/.X11-unix/X5` |
| `virgl` | Bind Termux's `.virgl_test` socket to `/tmp/.virgl_test` |
| `pulse_audio` | Bind Termux's `.pulse-socket` to `/tmp/.pulse-socket` |
| `selinux_permissive` | Request permissive SELinux handling for the container lifetime |

These options require an Android build and suitable host resources; unsupported
hosts or missing requested resources produce errors. They expose resources and
do not install or supervise Android applications or the corresponding host
services. See [Android root module](android-module.md) for installation and
boot startup.
